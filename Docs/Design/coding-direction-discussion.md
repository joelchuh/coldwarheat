# 正式编码前：实现方向讨论稿

description：在开始 C# 和 Unity 工程前讨论第一版交付、对象边界、测试方式和地图呈现顺序；这是建议，尚未授权实现。

用户目标是把《冷战热斗》做成本地双人优先、以后可联网与加入 AI 的电脑游戏。规则使用可复用模块和共享定义，地图与卡面可以更换画风。每批工作保留 JSON 描述、Wiki、来源和 Git 历史。本稿承接已有架构，不改变已确认的规则解释。

当前仓库主要是规则数据、契约、案例和文档。卡牌参数 Bound 表示参数已连接到设计登记，不代表事件运行处理器已经实现。离线 Python 检查器是验证设计的有限模型，不能直接拼成正式游戏，也不能把其中各自裁剪的状态对象当成多套生产 GameState。正式代码应从一个统一状态和命令管线开始。

## 三种起步方式

| 方式 | 最先得到什么 | 代价 |
|---|---|---|
| **推荐：纯规则闭环，然后占位地图** | 可重复验证的一次合法操作、拒绝行为、玩家视图；随后接地图点击 | 开始时画面很简单，但能尽早发现规则和接口问题 |
| 地图原型先行 | 更早体验世界地图、镜头和卡牌拖放 | 规则未接入时只能演示交互，之后仍需把临时状态替换为权威核心 |
| 先实现全部规则，再做画面 | 连续专注规则服务 | 很晚才能亲手体验，交互与流程问题发现较迟 |

建议采用第一种。完成一个真正可运行的闭环后，再按依赖加入事件、回合与整局玩法。完整规则组合仍会逐步设计和验证，不要求先把所有罕见组合都写成离线模拟器才能开始基础代码。

## 第一段代码的交付边界

第一批先创建 Core、Application 和测试入口。Core 不引用 UnityEngine；Application 绑定玩家身份、处理重复命令和投影。只读定义加载 84 国及已有规则数据；运行局面保存影响力、当前操作预算、版本号与必要的待处理状态。

第一个验收动作是“当前玩家用合法 OPS 在合法国家增加影响力”。必须能看到：成功只结算一次、非法目标不扣点、预算不足拒绝、过期新命令拒绝、重复命令返回旧结果、对手拿不到私有信息。先实现这个闭环，再加入 Fidel 这样的直接效果以及 Decolonization 这样的多国选择，从而验证数据驱动、效果组合与等待恢复确实可复用。

本批不以“能完整打完一局”为验收目标。完整本地对局仍需要头条、行动轮、全部行动规则、牌库、全部事件和组合，以及真实存档回放测试。每一个阶段用能操作或能真实运行的验收结果衡量，不用类的数量衡量进度。

## 面向对象的实现取向

静态 CountryDefinition、CardDefinition 与动态 CountryState、CardInstance 分离。实体用稳定 ID 引用定义，不复制印刷数值。GameState 是一个权威聚合，各服务返回变更计划或新状态；UI 不直接改它。

采用组合式效果与少量策略接口。增加影响力、移除影响力、选择、抽弃牌、计分与持续效果可以复用；复杂借牌事件拥有自己的策略，复用同一套父子帧。避免每张卡牌一串继承关系，也避免一个 GameManager 包含所有规则。

来源控制方、选择方、实际用牌者、OPS 行动者和根责任分别表达。各离线模型中的收据是验证设计的工具；生产客户端只发送意图，不能提交一个自己算出的完整 after_state 或成功标志来授权结果。真实结果必须由权威核心调用实际服务计算。

一条已接受命令提交状态、随机状态、事件与去重记录。坏输入不部分提交；已提交的前一步不会因后一条坏回调而倒退。待选择和子事件继续位置使用明确的数据类型，不保存 Unity 协程、闭包或动画回调。

## 地图与画风

先用能辨认国家、影响力、控制权与合法目标的占位表现。规则始终使用完整地图数据，局部视图只是展示范围。CountryId 对应布局坐标和选取区域；ThemeDefinition 对应卡面、材质、字体、音频等表现资源。

以后改为写实或其他风格，主要更换 Presentation、布局与资源。2D 改 3D 可能需要新的相机、选取和地图视图实现，但不应改变国家邻接、OPS、事件或胜负逻辑。尚未确定的画风不会阻挡规则闭环。

## 数据、存档和开发工具

沿用版本化 JSON 规则定义和描述索引。对局状态、命令记录和玩家视图分开；第一版本地存档可以用 JSON，数据库不属于第一个规则闭环的前置条件。未来房间、账号或大量对局检索再按实际需求选择存储适配器。

本机只读检查确认 Unity 编辑器为 `E:/unity6.6/6000.6.0f1/Editor/Unity.exe`，文件产品版本 `6000.6.0f1_f7f8ed4d1e24`。仓库目前没有 Assets 或 ProjectSettings；未启动或创建工程。实际 C#、API 和测试兼容性应在同意实现方向后通过最小工程核实，不在讨论稿中凭版本名推定。

已有 Wiki → catalog description → 模块描述 → 相关符号的检索顺序继续使用。新增生产模块配短描述、输入输出、依赖和测试入口；数据保持唯一来源。临时设计检查器不自动成为长期维护工具，稳定复用流程达到既有脚本化条件后才固化。

## 开工前需要共同确定

首先确认是否采用“纯规则闭环 → 占位地图 → 完整本地对局”的顺序，以及第一批验收是否接受从一次影响力操作开始。随后把已同意方向整理为小批实现计划，再进入 C# 或 Unity 工程；当前持续设计与额度授权不代替这一沟通。

规则裁定和工程选型分别记录。Missile Envy 的最高 OPS 比较与无可交换牌分支已由用户确认，限定按该牌的项目解释处理；其他未回答的边界不自动采用默认规则。未知来源、未接入消费者与真实运行测试继续显示各自状态。
