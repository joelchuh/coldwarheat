# 普通政变整体计划与收据

> description: 查询一次基础政变怎样组合军事/随机/影响力/DEFCON、防止重复掷骰、拒绝陈旧请求并一次形成完整After。
> 2026-10-14：纯C#计划50项新增测试，全量1561通过；宿主GameState与玩家出牌/地图命令尚未接入。

入口：[模块description](../Descriptors/coup-attempts.module.json) → Core/Rules/CoupAttemptState.cs（Create / Request / Receipt）及 CoupAttemptRules.PlanAttempt。共享数字复用[coup参数](../../Data/Descriptors/coup.data.json)、[军事参数](../../Data/Descriptors/military-operations.data.json)、[DEFCON参数](../../Data/Descriptors/defcon.data.json)，不复制业务表。

## 输入、过程、输出

Create为可信宿主创建一个同回合的不可变结算状态，包含GameId、revision0、基础定义、DEFCON/军事、精确覆盖规则地图的影响力、随机快照和显式活动效果快照。国家、效果和收据集合都防御复制且只读。Create没有恢复旧收据的能力，不能用它伪装存档恢复或随意重建同一局来逃过防重。

Request携带请求ID、GameId、来源行动/规则、原版本、回合、目标、Actor/PhasingPlayer以及分别核实的政变强度和军事信用。来源ID保留因果信息，本身不是行动授权。玩家不能提交这些可信数值；未来应用层需从会话与牌/预算策略生成。

PlanAttempt流程：

1. GameId/turn必须匹配；已保存的ID必须与全部原事实一致。合法重发直接返回当前状态和旧收据，不重新验证目标、不再次掷骰，也不把当前随机流或影响力倒退到旧结果。
2. 新请求必须匹配当前修订且记录未满；目标/核战/地理/敌方影响力及显式效果门禁先通过。
3. 先计划军事信用，内部ID为coup/请求ID；若信用已存在却没有对应政变收据，拒绝不完整状态。军事审核/溢出在取骰子之前阻止执行。
4. 外部随机源必须匹配状态中完整快照，独立Fork只在副本抽样；校验范围、算法/stream和推进计数。
5. 计算影响力，战场国无论成功都计划DEFCON降级；PhasingPlayer决定核战责任，可以不同于Actor。
6. 国家/军事/DEFCON/随机快照/新收据及递增修订组合成一个After；原状态和原随机源保持不变。失败不会只留下军事加点或消耗正式随机流。

后续宿主必须核对Before仍为当前权威状态，然后一次替换整份After。不得逐项重放Receipt中的军事实例/降级或随机值。新ID即使SourceActionId相同也不自动代表重复命令：根行动槽/剩余预算由宿主另管。核战后新操作拒绝，旧请求仍可无副作用地确认完成。

## 有意保留的边界

仅同一军事回合，尚无回合切换/完整存档、外部事件修改后聚合合并、卡牌去向或VP最终胜负流程。非核原因结束整局由未来GameResult门禁处理。任何非空活动效果集合都明确拒绝，不能据本模块宣称条约/危机/豁免已经支持。IRandomProvider是可信依赖，检查不能防止恶意实现隐藏共享内存。

4096收据/128效果ID是工程上限，不是桌游数值。上限拒绝新操作，但不影响合法重发。单元测试实际走完4096条并验证边界。
