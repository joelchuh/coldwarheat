# 模块描述、共享数据与脚本工作流

> description: 查找 JSON 描述约定、脚本化触发条件、共享规则数据组织、执行边界和每次工作的收尾流程。
> 状态：用户已确认并采用的工作约定。游戏模块、数据加载器、自动校验器尚未实现。
> 结构化策略入口：[workflow-policy.json](../Workflow/workflow-policy.json)。本页解释其用法，不是新增游戏规则。

## 1. 每次工作的检索顺序

先读根目录 AGENTS.md，再从 Wiki 摘要选择知识点。已有模块、脚本或数据目录时，先用小型 catalog 中的 id、description、status 和 descriptor 路径筛选，再读取命中项的完整描述。按其中的稳定路径和符号读取相关代码、调用方及测试；正确理解需要时扩大上下文。

JSON 是检索和约束说明，不是自动执行授权，也不是可以直接 eval 的程序。正式执行前核对参数、前置条件、环境、修改范围和停止条件。描述与代码不一致时先修复差异，不能因 description 匹配就盲目调用。

目前只有本工作流的策略 JSON。未来目录与描述文件随真实模块、脚本和数据集一起增加，不创建空目录或把规划当实现。

## 2. 哪些对象配描述文件

- 可独立理解或复用的模块：在模块旁放 module.json，覆盖其公开入口；不为每个私有函数单独建文件。
- 正式保留的工作脚本：同目录放同名 .script.json，记录解释器、参数、输入输出、数据依赖、副作用及失败边界。
- 数据集：配 .data.json；数据文件本身不必为了嵌入说明而改变其业务结构。
- catalog 只存筛选所需的少量字段，详细说明留在侧旁描述文件。条目增多、人工同步出现成本时，再依据脚本化条件决定是否生成目录。

描述的必备字段见策略 JSON 的 descriptor_policy.required_fields。路径统一相对于仓库根目录；入口使用文件路径和符号，行号只作辅助。无外部输入、依赖或副作用时用空数组明确表达；没有完成验证时 tests/verification 记录未执行，不填写虚假的通过结果。

数据描述补充主键、数据路径、schema 路径（仅在已存在时）、版本和来源。脚本通过 data_dependencies 引用数据集 ID，不复制数据集内容。

planned 状态的描述只能用于规划；entrypoints 不得指向尚不存在的实现。拟定符号放 planned_entrypoints。ready 表示对应实现可按声明使用，仍需满足调用前置条件；deprecated 表示有迁移说明、不再用于新工作。

## 3. 何时固化工作脚本

采用策略 JSON 中 script_creation.any_of 的两条路径：

1. 工作流的真实重复次数达到 min_observed_occurrences，预计还会复用，而且输入、输出和步骤已稳定。工作记录保存使用场景，不把同一次失败的机械重试当成成熟需求。
2. 边缘情况的处理流程已由用户明确确认，或由适用版本的权威规则确定。记录确认或来源及适用范围，不能凭“应该如此”固定流程。

两种条件之外，先完成当前任务并记录经验。一次性检查命令不必包装成长期脚本；准备保留复用时才进入上述门槛。正式脚本同步交付描述、关键成功/失败场景的验证和维护入口。

脚本应验证参数，限定读写路径，明确超时与重试次数。会写文件或外部服务时，提供可行的预览、备份或恢复办法；不能一概宣称所有操作可回滚。未知状态停止报告，不自动扩大权限或改写规则。Git 提交与推送由授权工作流程显式执行，不藏在一般业务脚本里。

## 4. 共享数据的组织

固定业务参数、卡牌定义和地图定义分别存放。动态 GameState 与静态定义分开；复杂判断、公式与结算顺序留在规则代码中。卡牌可用 effect_id 关联已注册效果，数值参数由数据提供；初期不引入通用规则脚本语言。

每个业务事实只有一个权威定义。脚本、规则模块和检查工具按稳定 ID 读取它；程序里的类型、枚举、字段名及定位用 ID 可以保留，不复制一套业务数值。Wiki 解释含义并指向数据来源。

未来有真实数据后，逐步采用：

| 规划位置 | 用途 |
|---|---|
| Data/catalog.json | 数据集摘要索引 |
| Data/Rulesets/<ruleset-id>/manifest.json | 规则集版本、数据文件清单和内容摘要 |
| Data/Rulesets/<ruleset-id>/rules.json | 固定规则参数 |
| Data/Rulesets/<ruleset-id>/countries.json | 国家基础数据与规则邻接 |
| Data/Rulesets/<ruleset-id>/Cards/ | 按时代组织卡牌定义 |
| Data/Descriptors/ | 数据集描述文件 |
| Data/Schemas/ | 随实际数据引入的结构约束 |

以上位置均为规划，尚不存在。先用 JSON 与内存字典；查询入口待规则和数据结构确定后实现。游戏侧可提供只读 GameDefinitions，脚本读取相同源数据。

程序解析整个 JSON 并不要求把全文交给模型；程序可缓存、建立字典，按 ID 和字段投影返回小结果。描述文件用于定位，不承担实际数据检索。

## 5. 校验与版本边界

数据进入正式规则集之前，需要检查字段和类型、ID 唯一性、跨文件引用、领域条件与来源版本。例如效果 ID 必须可解析，邻接国家必须存在。Schema 校验不能替代跨文件或规则正确性检查。

缺失、重复、冲突或尚未核实的数据明确拒绝或标为待核实，不能填入猜测的默认值。对局开始绑定规则集 ID、版本和数据摘要，存档保留同样信息；数据升级不得静默改变既有对局。

修改后的有效 OPS 等值属于本局计算结果，不能覆盖卡牌原始定义。关键规则测试的预期结果要独立推导并注明依据；不能仅把同一份数据读两遍就认为规则正确。

## 6. 收尾与下一步

每次变更同时检查代码/数据、描述、Wiki 和工作记录是否一致；记录实际验证，审阅后提交、推送并核对。项目 Skill 已要求先读 AGENTS.md 与 Wiki，因此通过这两个入口即可持续执行本约定，无须重复建立另一个 Skill。

本次只固化工作流与纠正本地同步状态，没有新增游戏源码、正式游戏数据或自动化脚本。下一步继续回合与出牌状态机的规则设计：阶段、行动资格、事件先后、待选择与卡牌去向；明确来源和验收场景，再展开风险与终局规则。
